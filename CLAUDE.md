# ScamBox (repo: FameChests, folder: Skrzynki)

ScamBox – gra webowa w otwieranie skrzynek (jak w CS) z kartami znanych osób. UI po polsku, bez monetyzacji.
Serwer w Rust (`server/`: axum + tokio + sqlx, PostgreSQL) + frontend w React (`web/`: React, Vite, TypeScript); aplikacja i pliki statyczne są wbudowane w `scambox.exe`. Repo: https://github.com/CebularzPawel/FameChests

## Frontend (`web/`)
- React 19, Vite, TypeScript, React Router, TanStack Query, Lucide (ikony zamiast emotek), Three.js (skrzynka 3D). Komponenty React Bits (`src/ui/reactbits/`, kopiowane do projektu): Counter, SpotlightCard, Galaxy. Każdą nową bibliotekę, także z React Bits, uzgodnić z użytkownikiem.
- Wygląd „Gablota”: tokeny w `src/styles/tokens.css`, prawie czarne tło, Hanken Grotesk + Bricolage Grotesque, karty w Rubik, kolor `--hue` z wybranej skrzynki. Bez emotek w interfejsie: Lucide albo tekst. Emotki zostają tylko na kartach (typ `types[t].icon`, koszt ataku, zdolności `abilityKinds`, plakietki `VARIANT_TAGS`) i na skrzynkach (emblemat to `emoji` skrzynki: model 3D `emblemTexture`, ikony, płaski rysunek), a także jako duszki na torze wyścigów (`horsesEngine.ts`).
- Dźwięki: nagrania CC0 w `static/sounds/`: skrzynki i kasyno z freesound.org (`fs-*.mp3`, autorzy w `CREDITS-freesound.txt`), interfejs, karty i szachy z paczek Kenney (`*.ogg`, `LICENSE.txt`); głośność każdego nagrania wyrównywana przy wczytaniu (`level`), mapa `SAMPLES` w `src/sound/sound.ts` (klucz dźwięku -> pliki, losowany jeden); syntezator Web Audio gra to, czego nie ma w nagraniach, i zastępuje nagranie, póki się nie wczyta. Nowy plik = dopisać do `static/sounds` i `SAMPLES`.
- Budowanie: `npm run build` w `web/` (`tsc --noEmit` + `vite build`, wynik `web/dist`, serwer podaje go pod `/app/` i jako stronę startową). Pliki .bat (`scripts/windows/`), `build_azure.bat` i `Dockerfile` robią to same. Tryb deweloperski: `npx vite` w `web/`, zapytania idą do serwera na porcie 5002.

## Struktura
- Wersja Python (`app.py`, `data.py`, `catalog.py`...) została usunięta (jest w historii git). Nazwy z niej w notatkach poniżej mają w Rust zwykle odpowiedniki o tej samej nazwie - szukać w `server/src` (np. `catalog.possible_variants` -> `catalog.rs`, `insert_item` -> `game/mod.rs`, `house_cards` -> `game/roll.rs`); „sekcja w app.py” = plik w `server/src/routes/`, „X w data.py” = klucz w `server/data/game.json` (camelCase: `VARIANTS` -> `variants`, `PATCH_NOTES` -> `patchNotes`, `HORSE_RACE` -> `horseRace`).
- `server/src/main.rs` + `routes/mod.rs` – adresy (`/api/...`), `routes/*` – endpointy wg zakładek (shop, casino, market, social, account, admin, arena, horses, variants), `auth.rs` – konta, sesja, `login_required` / `admin_required` jako ekstraktory.
- `server/data/game.json` – ustawienia gry (ceny, rzadkości, warianty, secretOdds=2137, skrzynki daily/mega, osiągnięcia wbudowane, wyścigi) i wbudowane karty; JEDYNE źródło danych gry - edytować bezpośrednio (wartości wyliczane w `data.rs`, pilnuje ich `cargo test`).
- `server/src/catalog.rs` – łączy `game.json` ze zmianami z panelu admina (tabele `catalog_crates` / `catalog_cards`); karta może być w kilku skrzynkach (`crates`), szansa na tajną liczona automatycznie. `variants.rs` – ustawienia wariantów, naklejki, kreator (`catalog_variants`).
- `server/schema.sql` – schemat PostgreSQL (jedyny; start serwera wykonuje go przy każdym uruchomieniu). Nowa tabela: tylko tam. Nowa kolumna w istniejącej tabeli: osobna linia `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (samo dopisanie do `CREATE TABLE` nie zmieni istniejącej bazy; ewentualna migracja danych w `startup.rs`).
- Start (`init_db`, uzupełnienia `backfill_*`) przy bazie w chmurze: każde zapytanie to podróż przez sieć - wiele wierszy wstawiać paczkami `insert_rows(conn, "INSERT INTO t (a, b) VALUES", rows)`, nie pętlą pojedynczych INSERT-ów (tysiące zapytań przekraczały limit startu na Azure - `startupTimeLimit` w `deploy/azure/web.config` - i proces był ubijany przed commitem, strona nie wstawała).
- Endpointy, które sprawdzają stan gracza i go zmieniają (pieniądze, karty, skrzynki), zaczynają się od `lock_me()` – inaczej podwójne kliknięcie wydaje to samo dwa razy.
- Właściciel i kopie bazy: rola ponad adminem tylko z `OWNER_IDS` (zmienna serwera, nie baza/panel; `Config::is_owner`, ekstraktor `auth::Owner`). Tylko owner: zakładka „Kopie zapasowe” (`/admin/backups`, `BackupsAdmin.tsx`, `/api/admin/backups*` w `routes/backups.rs`, widoczność z `/api/admin/role`). Pierwsze konto NIE jest adminem z automatu; `startup::init_db` nadaje admina kontom z `OWNER_IDS` (bez tego na świeżej bazie nikt nie nadałby pierwszego). Akcje admina na cudzym koncie, które pozwoliłyby je przejąć albo zniszczyć (link do resetu hasła, admin, blokada, usunięcie konta i kart), zaczynają się od `guard_owner` w admin.rs - nowa taka akcja też. Admin nie ustawia graczom hasła: przycisk „Reset hasła” w Graczach (`resetLink` w panel.ts, `/api/admin/users/<id>/reset-link`, `admin_reset_link`) wysyła mail z linkiem tym samym `account::send_recovery` co „zapomniałem hasła” (Supabase Auth `recover`) - na wpisany adres albo, gdy pusty, na email z `user_auth` gracza; gracz bez emaila (`user_auth` puste - zgubił hasło przed dodaniem emaila) nie ma konta w Supabase Auth, a `recover` wysyła tylko do istniejących kont, więc wpisany adres jest mu najpierw przypisywany (`account::admin_attach_email`: `GoTrue::admin_create` z losowym hasłem i potwierdzonym emailem + wiersz `user_auth`, przy nieudanej wysyłce konto w GoTrue jest cofane); odpowiedź zawsze ta sama (nie zdradza, czy adres ma konto), dziennik `password_link` z zamaskowanym adresem. Gdy jest `SMTP_URL`, ten sam reset idzie własnym mailerem gry (tokeny niżej), nie przez GoTrue. „Zmień email” w Graczach (`/api/admin/users/<id>/email`, `admin_set_email`, też za `guard_owner`, dziennik `email_change`): gracz z emailem -> `account_mail::change_email` + powiadomienie na stary adres, bez emaila -> `admin_attach_email`. Kopie: `backup.rs` (`pg_dump` schematu gry do `BACKUP_DIR`, automatyczne co `BACKUP_EVERY_HOURS`, rotacja `BACKUP_KEEP`, pobrać da się tylko nazwy z `valid_name`); obraz Dockera ma postgresql-client-17.
- Panel admina: JEDNO menu (`adminMenu.ts` = jedyne źródło: grupy Katalog / Gracze / Treści / Gry / System (tylko owner), pozycje, opisy, adresy; rysuje je `AdminApp.tsx`). Komputer: pionowy pasek boczny, który się NIE przewija (gdy pozycje się nie mieszczą, grupy zwijają się w akordeon, a „Więcej” otwiera pełną listę w oknie; liczy `fit()` + ResizeObserver); telefon (do 820 px): górny pasek z nazwą pozycji i przyciskiem „Menu” = pełnoekranowe `role=dialog` (Esc, focus trap). Adresy: pozycje z `panel.html` przez `/admin#<id>` (np. `/admin#maile`; elementy mają `data-sec="<id>"`, pokazuje je `showSection` w `sections.ts`, kilka id po spacji), strony osobnymi ścieżkami (/variants, /admin/events, /admin/chess...). Stare hashe `#crates #cards #players #content #games` przechodzą na pierwszą pozycję grupy; ostatnia pozycja w `localStorage` `adminItem`; pole „Szukaj w panelu” filtruje menu. **Nowy panel = dopisać pozycję w `adminMenu.ts`** (+ `data-sec` w panel.html albo stronę w `page()` w AdminApp.tsx), inaczej zawsze będzie widoczny / nie będzie w menu. Telefon: zero przewijania w bok (sprawdzać `scrollWidth <= innerWidth` przy 375 px); tabele zamieniają się w karty (`mobileTables.ts` dopisuje `data-label` z `thead`, CSS `td::before` w admin.css, więc nowe tabele działają same), pola i okna na całą szerokość, długie teksty `overflow-wrap: anywhere`. Wyszukiwarki długich list: `listSearch.ts` (`attachSearch`, `watchLists` - lista `LISTS` selektorów; lupa, licznik „X z Y”, Esc czyści, bez polskich znaków); nowa długa lista = dopisać wpis do `LISTS`. Zakładka Szachy nie ma podziału. Dział Karty (`cardsTool.ts`): wyszukiwarka wszystkich kart (po nazwie, id, podtytule, ataku, zdolnościach, skrzynce; filtry rzadkość / skrzynka / typ / bez zdjęcia / własne...; tajna karta bez „Pokaż tajne” szuka się tylko po rzadkości), „+ Nowa karta” (formularz `openCardForm(null, skrzynka)`) oraz eksport i import kart.
- Import i eksport kart (`routes/cards_io.rs`, `/api/admin/cards/export` POST, `/template` GET, `/import` POST): JSON (`{"format":"scambox-cards","cards":[...]}` albo sama lista; pełne karty z Areną, napisami, źródłem, `fixedVariant`) i CSV (separator `,` `;` albo tabulator, kolumny `id,name,rarity,type,crates,...,ability<n>name/kind/value`, UTF-8). Klucze pól jak w eksporcie; rzadkość, typ i skrzynkę można podać też nazwą. Wiersz przechodzi to samo sprawdzanie co formularz karty (`prepare`): z `id` istniejącej karty = zmiana tylko podanych pól (`save_override` scala), bez `id` = nowa (z listą zdjęć `imageUrl` / artykuł `wikiTitle`), nowa karta o nazwie, która już jest w skrzynce, jest pomijana. „Sprawdź” (`dryRun`) niczego nie zapisuje; przy błędach nie zapisuje się nic, chyba że `partial`. Najwięcej 500 kart. Dziennik: `cards_import`. Nowe pole karty = dopisać w `prepare`, `card_value`, (jeśli płaskie) `CSV_COLUMNS` i w `field_specs`. Wzór (`/template`) jest generowany z aktualnego katalogu: JSON ma na górze `_instrukcja` i `_pola` (opis, wymagane, typ, `dozwolone` {wartosc, nazwa} dla rzadkości, typów, skrzynek, rodzajów zdolności, źródeł, wariantów), CSV ma linie komentarza `#` z tymi samymi listami; import pomija klucze `_` w JSON oraz linie `#` i puste w CSV (komentarz `#` tylko na początku wiersza). Importu skrzynek nie ma.
- Maile Supabase Auth (potwierdzenie konta, nowe hasło, zmiana emaila) mają własny HTML w kolorach gry: `server/email/*.html` (wygenerowane tabelami i inline CSS - klienty poczty nie czytają zewnętrznych arkuszy; pola `{{ .ConfirmationURL }}` / `{{ .Email }}` / `{{ .NewEmail }}` muszą zostać, pilnuje tego test w account.rs). Gra podaje je na `/email/<nazwa>.html` (`account::email_template`), GoTrue pobiera je przez `GOTRUE_MAILER_TEMPLATES_*` (`deploy/selfhost/docker-compose.override.yml`); lokalnie `supabase/config.toml` wskazuje te same pliki.
- Własna poczta gry (`mailer.rs`, `SMTP_URL` np. `smtp://mailpit:1025` albo osobno `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS` jak w GoTrue - 465 TLS, 587 STARTTLS; `MAIL_FROM`, bez niego `SMTP_SENDER_NAME` + `SMTP_ADMIN_EMAIL`, zły adres nie zatrzymuje serwera, `PUBLIC_URL` lub adres z nagłówka Host w linkach; bez `SMTP_URL` mail trafia tylko do logu serwera razem z linkiem): reset hasła (admin, „zapomniałem”, `POST /api/account/password/send-link`) i zmiana emaila (`/api/account/email-change/request` -> mail na OBECNY adres z linkiem `/konto/email?t=...` -> `.../confirm` z nowym adresem, `EmailChangePage.tsx`; `change_email` robi `GoTrue::admin_set_email`, jeśli konto jest w GoTrue, i wysyła `email_changed_notice` na stary adres). Tokeny jednorazowe `tokens.rs` (tabela `account_tokens`, w linku `sb1_` + 32 bajty hex, w bazie sha256, ważność `TOKEN_TTL` = 1 h, nowy token danego rodzaju unieważnia starsze; `consume` jest atomowym UPDATE ... RETURNING). Link resetu: `/login?t=sb1_...` -> `POST /api/account/reset` (token `sb1_` vs JWT GoTrue rozróżnia `LoginPage.tsx`). Szablony: `mail_templates.rs` + domyślne `server/email/*.html` (confirmation, recovery, email_change dla GoTrue oraz password_reset, email_change_request, email_changed_notice), nadpisane w panelu „Maile” (`mailTemplates.ts`, `routes/mail_admin.rs`) lądują w `email_templates`; podstawianie `{{ .Pole }}` z escapowaniem, zapis sprawdza wymagane pola i odrzuca nieznane. Nowy szablon = wpis w `DEFS` + plik html (wszystkie maile mają jeden układ w kolorach `tokens.css`: tabele + inline CSS, ciemne tło, przycisk w kolorze akcentu). Potwierdzanie emaila bez GoTrue, z SMTP (`verify_by_mail`): szablon `email_verify`, token `email_verify` ważny 24 h (`tokens::ttl`), link `/konto/potwierdz?t=` (`VerifyEmailPage.tsx`), kolumna `user_auth.verified_at`; logowanie nie czeka na potwierdzenie. `account::on_email_verified` jest JEDYNYM miejscem po każdym potwierdzeniu (link, pierwsze logowanie przez GoTrue, reset hasła linkiem) - tam podpinać skutki (np. nagrody za polecenia). Tryb bez GoTrue: wiersz `user_auth` z `auth_id` = `local:<id>` (email tylko w grze, hasło w hashu gry); `AuthLink::is_local()` - takie konto nigdy nie trafia do GoTrue (logowanie, zmiana hasła, usuwanie, resend), nowa ścieżka używająca `auth_id` musi to sprawdzać. `own_mail()` = gra sama wysyła maile (jest SMTP albo nie ma GoTrue); przy GoTrue bez SMTP działa stara ścieżka `recover`.

Azure App Service (Windows): `build_azure.bat` -> `dist\scambox-azure.zip` (exe + `deploy/azure/web.config`), `docs/hosting.md`.

- Osiągnięcia (`server/src/achievements.rs`, panel admina „🏆 Osiągnięcia” - `static/js/achievements-admin.js`, gracz: `static/js/achievements.js` + panel na profilu `#pfAch`): definicje w tabeli `achievements` (JSON: 1-2 warunki `criteria` + `rewards`: pieniądze / skrzynki / karty, `hidden`, `enabled`; wbudowane z `achievements` w game.json wpisywane raz przy starcie (`achievements::init`), usunięte mają `deleted`), liczniki zdarzeń gracza w `user_counters` (klucze z `achievements.card_events` / `play_events` / `win_events` / `open_events`), zdobyte w `user_achievements` (`seen` - popup). Zdarzenia tylko wołają `ach_count(user_id, klucze)` (bufor w `g`); po udanym zapytaniu `ach_after` zapisuje liczniki, sprawdza osiągnięcia zalogowanego gracza (`ach_award`, też w `/api/me`, żeby złapać rywala z jackpota / Areny), daje nagrody i dopisuje nagłówek `X-Ach` - `api()` w app.js woła wtedy `achPoll` (popup + odświeżenie ekwipunku). Warunki z kartami liczą max(liczniki, karty w ekwipunku teraz - `ach_owned`), więc działają też karty z wymiany / rynku / jackpota. Seria wygranych w kasynie (`casino_streak`, klucze `streak:` / `beststreak:` zapisywane od razu w `ach_casino`; `won=None` = remis, nie przerywa), dzień tygodnia gry (`weekday` w `casino_plays`, klucze `play:<gra>:wd<n>`), `drop_together` z powtórzeniami (dwie takie same karty naraz). `/api/me` zwraca `achUnseen` (popup, gdy nagłówek X-Ach przepadł, np. przy `fetch` w jackpocie). Popupy czekają na koniec animacji (`achPump` / `animBusy` w achievements.js: bęben skrzynki do `S.opening.shown`, epickie otwarcie, `CS.spinning` w kasynie, `S.animHold` - np. wynik jackpota), żeby nie zdradzać wyniku; nowa animacja z wynikiem = dopisać tam jej warunek. Na profilu dwie zakładki: zwykłe / ukryte (`achProfileDraw`). Nowy rodzaj warunku: `achievements.rs` (`criterion_key`, `clean_criterion`, `describe`) + pole w `aeCritFields` + hak zdarzenia. Stare konta dostają liczniki z ekwipunku (`backfill_achievements`). Osiągnięcia z kartami, których jeszcze nie ma w grze (Lech Kaczyński, Netanjahu), są wyłączone, dopóki admin nie wskaże karty. ## Serwer w Rust (`server/`)
- Tylko PostgreSQL (lokalnie `docker compose -f docker-compose.local.yml up -d db` w głównym folderze - localhost:5433, produkcja: Supabase - session pooler, port 5432). Szczegóły: `server/README.md`, instrukcje (uruchamianie, hosting, przejście, rozwój): `docs/`.
- Zapytania: `sqlx::query!` / `query_as!` / `query_scalar!` (sprawdzane przy kompilacji); po zmianie zapytań `cargo sqlx prepare` i commit `server/.sqlx/` (budowanie bez bazy: `SQLX_OFFLINE=true`). Zapytania bez makr (`sqlx::query(...)`) nie wymagają `prepare`; sqlx 0.9 przyjmuje tylko stałe napisy SQL (sklejanie: `concat!`).
- `lock_me` = `db::lock_me(&mut tx, uid)` na początku transakcji; błąd (`bad(...)`) porzuca transakcję.
- Zapytania z przeglądarki: `JsonBody<T>` ze strukturą `Deserialize` przy handlerze, odpowiedzi: struktury `Serialize` (camelCase, klucze jak w `static/js`); pola formularzy admina z liczbami jako tekst - `lenient.rs`.
- Hasła w formacie werkzeug (scrypt) – te same hashe co w dawnej wersji Python. Sesja: podpisane ciasteczko `scambox_session`.
- Osiągnięcia: zdarzenia wołają `achievements::count*` (liczniki od razu w transakcji), a warstwa `achievements::layer` po udanym zapytaniu sprawdza osiągnięcia i ustawia `X-Ach` / `X-Bibi`.
- Testy: `cargo test`, `cargo clippy --all-targets`.

## Uruchamianie
- Test lokalny w Dockerze (bez Rusta i Node): `lokalnie.ps1` / `lokalnie.sh` = `docker compose -f docker-compose.local.yml up --build` - gra (:8000) + testowa baza (127.0.0.1:5433, wolumen `scambox-local-db`) + Mailpit (:8025, tu lądują maile; `SMTP_URL`), dane w `data-lokalne/` (git-ignore), porty w `.env` (wzór `.env.example`). Konto testowe `admin`/`admin` tworzy start gry z `DEV_ADMIN_USER` + `DEV_ADMIN_PASSWORD` (`startup.rs::ensure_dev_admin`, tylko gdy gracza nie ma, od razu admin) - nigdy na produkcji. Rust nie ma live reload: po zmianie kodu ponownie uruchomić skrypt. Zaczynanie od zera: `down -v` + usunąć `data-lokalne/`.
- Układ repozytorium: katalog główny = `README.md`, `CLAUDE.md`, `Dockerfile` (kontekst = katalog główny), `docker-compose.local.yml`, `lokalnie.*`, `.env.example`; `server/`, `web/`, `static/`, `docs/`, `deploy/`, `supabase/`, `seed/` (`catalog_export.json` + `custom_images/` - dane startowe katalogu i cel `export-catalog`), `scripts/windows/` (bat-y), `data/` (git-ignore, domyślny `DATA_DIR`).
- `scripts/windows/start_tailscale.bat` (hosting dla znajomych), `start_lan.bat` (sieć lokalna), `start.bat` - wszystkie budują `web/` i robią `cargo run --release` w `server/` (potrzebne `server/.env` z `DATABASE_URL`, np. do bazy z docker-compose.local.yml).
- `cargo run --release -- [--dev] [--lan] [--test]`, port: zmienna `PORT`; `--test` = osobna baza testowa (`TEST_DATABASE_URL`) na porcie 5001 (na tym komputerze 5001 zajmuje VirtualBox - użyj `PORT=5002`). Druga kopia na zajętym porcie się nie uruchomi.
- Po każdej zmianie kodu użytkownik musi zrestartować grę (Ctrl+C i ponownie .bat).
